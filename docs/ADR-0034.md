# ADR-0034: Tropical Max-Plus Router Production Benchmark Harness, Empirical Invariant Verification, Living Reporting, and CI/CD Alignment

## 1. Context and Problem Statement

The **Tropical Max-Plus Router** (`/run/media/multiplic/AGI/prismagi/mount/ROUTERS/tropical-max-plus`) is the LexLean Language 1.2 formalization of max-plus routing arithmetic: `tropicalMul(w, x) = w + x`, `tropicalScore(w, x, b) = tropicalMul(w, x) + b`, and the kernel-certified smoke theorem `router_smoke_eval : tropicalScore 3 5 2 = 10`. It is compiled and published through PrismPM 0.5.0 on Lean `v4.32.2`.

A baseline recompilation established:

- PrismPM build digest: `1027857c266519abf79bcbd6d5dd95ed72f0d731ca7c66ecb3e250f3029dfa90`
- LexLean semantic ID: `afd80884608e37187f0bf6808c47b48d96551b3b529146b4757349b35d14d142`
- Attestation ID: `3245a2c5642fc4c8fbda090c436682597d32764c27029ba434cc41ce3d897860`
- Compiler semantics: `4b3ed2378d6c43bb32a41d466cf140337e8b1cedc5e1f345aaf3395f488f63a9`

That recompilation only succeeded after repairing stale pins (`leanprover/lean4:v4.32.1` → `v4.32.2`, compiler semantics `1427f8b6…` → `4b3ed237…`, and rewritten SHA-256 hashes in `lexlean.lock`). The defect was discovered at release time rather than at commit time. Production readiness therefore requires:

1. Continuous detection of toolchain, lockfile, and compiler-semantics drift before a commit is admitted.
2. Empirical stress testing of the max-plus semiring laws and checked 64-bit arithmetic under high-volume deterministic workloads.
3. Reproducible build and report verification so the published digest and human-readable evidence cannot diverge.
4. Zero-drift living documentation generated directly from execution receipts and staged into version control.
5. Fail-closed local and remote gates with published, human-readable CI summaries.

This decision establishes reference parity with [`kuramoto-protocol-r3`](file:///run/media/multiplic/AGI/prismagi/mount/SUBSYSTEMS/kuramoto-protocol-r3) (ADR-0024/0025/0026) and the router lineage in ADR-0033, while respecting the Language 1.2 constraint that verification must be driven by PrismPM rather than the standalone language-1.0 `lexlean` CLI.

## 2. Decision Drivers

- **Shift-Left Assurance**: Toolchain drift, stale locks, and proof regressions must fail at pre-commit, not during release.
- **Mathematical Rigor**: Max-plus algebra laws and overflow containment are exact-integer properties; they must be tested with zero tolerance and deterministic seeds.
- **Reproducibility**: Identical inputs must yield identical build digests, semantic IDs, and canonical report bytes.
- **Zero-Drift Documentation**: Markdown and JSON evidence must be regenerated on every run and atomically staged with source changes.
- **Fail-Closed Automation**: Pre-commit and GitHub Actions must halt on any failure, with reports still uploaded for diagnosis.
- **Standards Alignment**: Traceability to NIST SP 800-53 (`SI-7`, `SA-11`, `CA-2`, `CM-3`, `AU-10`, `CP-2`) and ISO/IEC 25010, 27005, and 42010 expectations.
- **Honest Gate Scope**: `prismpm verify` currently exits `PP5003` because the snapshot contains no Prism declarations; it must be declared informational rather than silently omitted or falsely claimed as passing.

## 3. Decision Outcome

We adopt a **Production-Grade Tropical Router Verification Harness and CI/CD Alignment Gate** with the following components.

### 3.1 Nine-Suite Unified Runner (`run_tests.py` / `run-tests.sh`)

1. **TS-01 — Toolchain & Runtime Pin Audit**: validates Lean `4.32.2`, PrismPM `0.5.0`, Python ≥ 3.11, and pinned configuration files.
2. **TS-02 — Lake Host Workspace Build**: runs `lake build` and verifies the Lean host manifest.
3. **TS-03 — LexLean Lock & Canonical Configuration Parity**: recomputes SHA-256 for `lexlean.toml`, `lakefile.toml`, `lean-toolchain`, and `lake-manifest.json`; asserts lock compiler semantics and toolchain pins match the baseline.
4. **TS-04 — PrismPM Static Model Check**: runs `prismpm check` and requires zero `PPxxxx` diagnostics.
5. **TS-05 — Lean Kernel Attestation Audit**: verifies `.lexlean/verified/*/attestation.json` has `status: verified` and a matching semantic ID, and that every `TropicalRouter.*` project declaration has an empty observed-axiom set. Runtime declarations governed by `exact` axiom policies are outside this project-declaration gate and are reported separately.
6. **TS-06 — Formal Router Theorem Audit**: confirms `tropicalMul`, `tropicalScore`, and `router_smoke_eval` exist with `decide` proof and expected evaluation.
7. **TS-07 — PrismPM Build & Manifest Integrity**: runs `prismpm build`, compares the emitted digest to the pinned baseline, and verifies every SHA-256 in `.prism/build/<digest>/manifest.json`.
8. **TS-08 — Tropical Benchmark Engine**: executes the five-sub-suite empirical engine defined below.
9. **TS-09 — Reporting & Gate Contract Integrity**: validates report freshness, dual-format retention, and fail-closed hook/workflow configuration, including negative fault injection.

### 3.2 Five-Suite Empirical Benchmark Engine (`benchmark_tropical_router.py`)

- **SUITE-S1 (`INV-TRP-034a`) — Max-Plus Semiring & Score Algebra**: 10,000 seeded integer triples over `[0, 2^32]`; verifies `tropicalMul = +`, associativity, commutativity, idempotence of `max`, and `tropicalScore = tropicalMul + b`. Zero violations permitted.
- **SUITE-S2 (`INV-TRP-034b`) — Checked Overflow Containment**: boundary sweep over `0`, `2^32−1`, `2^32`, `2^63−1`, `2^63`, `2^64−1` plus 5,000 near-limit random pairs; every overflow must raise the checked sentinel; zero silent wraps.
- **SUITE-S3 (`INV-TRP-034a`) — Routing Table Scale & Latency**: table sizes `N ∈ {10, 100, 1,000, 10,000, 100,000}` with 5 warmups and 20 measured repetitions; records p50/p95/p99 and throughput; throughput must be ≥ 90% of pinned baseline.
- **SUITE-S4 (`INV-TRP-034c`) — Build & Semantic Reproducibility**: two consecutive builds and report generations with unchanged inputs must produce identical digest, semantic ID, and canonical report hashes (timestamps excluded).
- **SUITE-S5 (`INV-TRP-034e`) — Gate Evidence Integrity**: injects a stale-lock fault and a failing-suite fault into a sandbox copy; both must exit non-zero and stage no reports.

Every random workload uses a recorded fixed seed; every timing table records warmup/repetition counts, host OS/arch, Python version, and toolchain versions.

### 3.3 Living Documentation & Continuous Assurance

- **Dual-Retention Reports**: `reports/TEST_REPORT_LATEST.md`, `reports/test_report_latest.json`, `reports/STRESS_BENCHMARK_LATEST.md`, `reports/stress_benchmark_latest.json`, plus immutable timestamped copies.
- **Automated Content**: toolchain pins, compiler semantics, semantic ID, PrismPM digest, suite matrix, benchmark tables, verdicts, environment metadata, and companion JSON hashes.
- **Local Gate**: `install-hooks.sh` installs `.githooks/pre-commit`; the hook runs the full harness, aborts on failure, and stages `reports/` only on success.
- **Remote Gate**: `.github/workflows/verify-test.yml` triggers on push/PR to `main`/`master`, uploads reports with `if: always()`, and publishes both Markdown reports to `$GITHUB_STEP_SUMMARY`.

### 3.4 Explicitly Deferred Gate

`prismpm verify` remains **non-blocking and informational** in ADR-0034 because the current snapshot contains no Prism declarations (`PP5003`). Promotion to a blocking suite requires an amendment that introduces Prism declarations and records a passing attestation. This is a scope decision, not a suppression of a failing check.

## 5. Consequences

### Positive
- Toolchain, lockfile, and compiler-semantics drift is detected before commit.
- Tropical algebra and overflow behavior receive empirical coverage complementary to the `decide` kernel proof.
- Published build digest, semantic ID, and human-readable reports are mutually consistent and reproducible.
- Reviewers read results directly in GitHub job summaries without parsing logs or JSON.
- Full control traceability supports audit and accreditation workflows.

### Negative / Trade-Offs
- Local pre-commit verification is expected to add roughly 10–25 seconds for Lake build, PrismPM check/build, and benchmark repetitions.
- Exact 64-bit overflow behavior is emulated in the Python benchmark and must remain synchronized with the Rust production target definitions; target changes require a baseline update.
- Two consecutive builds in S4 double PrismPM build cost on every full run; a `--fast` hook mode may run S4 only on release branches after baseline accreditation.
- `prismpm verify` remains deferred until Prism declarations exist, which leaves a coverage gap explicitly documented above.

## 6. Alternatives Considered

| Alternative | Reason for Rejection |
| :--- | :--- |
| Rely solely on `prismpm check && prismpm build` at release time | The stale-pin failure was discovered only at release; no shift-left protection. |
| Use standalone `lexlean check`/`lexlean verify` as in Kuramoto | Installed standalone CLI is language 1.0 and rejects this project's `lexlean/project/1` language 1.2 configuration; PrismPM is the authoritative compiler. |
| Markdown-only reports | No reliable machine gate, diffing, or CI assertion surface. |
| JSON-only reports | Poor human reviewability and no step-summary value. |
| Treat `prismpm verify` as blocking today | It deterministically fails with `PP5003` for this model; blocking would make CI permanently red without adding signal. |

## 7. Implementation Status

Implemented under [`PLAN-ADR-0034.md`](PLAN-ADR-0034.md):

- `run_tests.py` / `run-tests.sh` — authoritative 9-suite runner and dual-format reporter.
- `benchmark_tropical_router.py` — five-sub-suite empirical benchmark and fault-injection engine.
- `.githooks/pre-commit` / `install-hooks.sh` — fail-closed local gate with report staging; documentation-only commits skip the harness so evidence is not regenerated without behavioral changes.
- `.github/workflows/verify-test.yml` — fail-closed remote pipeline with artifact upload and step summaries.
- `reports/` — `LATEST` Markdown/JSON plus immutable timestamped receipts.

Baseline run `20261124T193309Z`: **9/9 suites PASS**, **5/5 benchmark sub-suites PASS**, build digest `1027857c…`, canonical report SHA-256 `39485d72e18a49cd8b8a21c207f0fcd50d0ec9ef7b4cfd7680cd6551f536c127`. The pre-commit hook is staged but not installed because the subsystem is not currently a git work tree; `install-hooks.sh` reports this explicitly and installs it once `.git` exists.
